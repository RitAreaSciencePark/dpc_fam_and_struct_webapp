# DPCexplorer Admin Panel: What it does, How it works, and Why

> 📌 This note is for anyone who administers DPCexplorer, whether you run the tool on your own machine or in production.

In Django, you create an administrator with a single command:

```bash
python3 manage.py createsuperuser
```

You then fill in the credentials, and that account receives full **CRUD** (Create, Read, Update, Delete) over every table by default. Because DPCexplorer publishes a scientific dataset, we did not want that power switched on silently. Instead, we placed it behind one clear switch, so the panel ships safe and you still decide its behavior at deployment time.

---

## 🔐 Two possibilities, one build

The behavior is controlled by a single setting, `DPCEXPLORER_ADMIN_WRITABLE`, which we read from your `.env` file. We offer two possibilities:

- **The default (`False`), read-only.** This preserves the **FAIRness** of the project and avoids any issue related to human error from the admin panel. An administrator can read every table, but cannot write to them, not even a superuser. Add, Change, and Delete simply disappear.
- **The second (`True`), full freedom.** This hands full CRUD back to the administrator, who is then responsible for any change they make. Permissions fall back to Django's normal per-user rules, so a superuser can write freely and other staff write according to what they were granted.

> ✅ Safe by default: the data is never writable by accident. Write access exists only when someone deliberately turns it on.

To switch, set one line and restart the server:

```bash
# read-only (default, recommended)
DPCEXPLORER_ADMIN_WRITABLE=False

# full CRUD
DPCEXPLORER_ADMIN_WRITABLE=True
```

You will always know which mode is live: the admin landing page reads **"Read-only data console"** or **"Read/write data console"**, and the mode is written to the logs the moment the server starts.

---

## 🔄 Changing the data the right way

Even with write mode on, the admin panel is not the right tool to edit the bulk of the scientific data. That data is produced by our pipeline, which stays the single source of truth. Should you need to change it, rebuild from the pipeline rather than editing rows by hand.

The cleanest path is to drop the database and reload it. See the README section **[Hints for Common Situations → Dropping the database and user (clean reset)](README.md#hints-for-common-situations)**, which resets `dpcexplorer_db` / `dpcexplorer_admin` and sends you back to **Step 4**. If you populated the tables with the automated script (`setup_dpcexplorer_data.sh`), update the data sources it points to and run it again.

> ⚠️ A hand-edit through the admin lives nowhere in the pipeline. On the next rebuild it would be lost, or worse, it would quietly disagree with our published Zenodo records.

## ⚙️ How it works (under the hood)

- **A mode-aware base class.** `DpcBaseAdmin` in `dpc/admin.py` denies Add, Change, and Delete unless `DPCEXPLORER_ADMIN_WRITABLE` is on; when it is on, it defers to Django's per-user permissions. Viewing is always allowed, so in read-only mode each detail page renders as a read-only form. The switch is read at request time, so a single build serves both modes. `dpcfam/admin.py` and `dpcstruct/admin.py` import this base, so every model behaves the same way.
- **Tuning for the large tables.** `LargeTableAdmin` serves the four big tables, DPCfam sequences (~16.6M rows), the protein registry (~14.1M), the UniRef50 to Pfam mappings (~14.55M), and DPCstruct sequences (~1.64M). It replaces the slow default substring search with an exact, index-backed lookup, so a query uses the primary-key or foreign-key index instead of scanning the table.
- **Cheap row counts.** `EstimatedCountPaginator` reads PostgreSQL's planner estimate (`pg_class.reltuples`) on an unfiltered page instead of running a full `COUNT(*)`, then falls back to the exact count once a filter narrows the rows. The totals shown on the big tables are therefore approximate by design.
- **Safe write widgets.** Every admin with a foreign key sets `raw_id_fields`, so even in write mode a relation field never tries to load millions of related rows into a dropdown.
- **Clean names and branding.** Each model declares its `verbose_name`, and each app its own in `apps.py`, so the sidebar reads cleanly (DPC Core, DPCfam, DPCstruct). The site header and the mode subtitle are set in `urls.py`.

---

## 💡 Why we built it this way

- **Safe by default.** Shipping read-only means the data is never writable unless an operator consciously enables it. Anyone reviewing the project sees a safe artifact, not write access baked into a release.
- **FAIRness and provenance.** The database is generated by a reproducible pipeline. Keeping the default read-only keeps that pipeline the single source of truth and protects the published, citable record.
- **One version, two postures.** The switch is configuration, not a second codebase. Later fixes land once, and you choose read-only or full CRUD per deployment.
- **Honest about the residual risk.** In write mode, CRUD is real: deletes follow the `on_delete=CASCADE` foreign keys, so removing one parent row removes its dependent rows. Enable it deliberately, and prefer the pipeline for any change meant to last.

## 🗂️ Where this lives

| File | Role |
|------|------|
| `dpc/admin.py` | `DpcBaseAdmin`, `LargeTableAdmin`, `EstimatedCountPaginator`, the `admin_writable()` helper, and the `dpc` registrations |
| `dpcfam/admin.py`, `dpcstruct/admin.py` | the remaining registrations |
| `*/models.py`, `*/apps.py` | the `verbose_name` declarations |
| `dpc_fam_and_struct_webapp/settings.py` | the `DPCEXPLORER_ADMIN_WRITABLE` flag |
| `dpc_fam_and_struct_webapp/urls.py` | the admin branding and mode subtitle |

> 💬 Should you add a new data model, register it against `DpcBaseAdmin` (small table) or `LargeTableAdmin` (large table, with `exact_search_fields`). It then inherits the same mode switch, performance, and naming behavior.
